# E20 — Languages (L10N)

## 1. Summary

Guests can use Mehfil in **English, Hindi and Kannada**: the React Native Guest mode, the guest lite web page, push/SMS text and WhatsApp templates. Host-written text (event names and notes, dress codes, venue notes, key-contact labels, announcements) is machine-translated and reviewed by the host. Dates and times follow local formats in the wedding's timezone.

| Stories | Sprint |
| --- | --- |
| L10N-01 Hindi, L10N-03 language preference + content translation, L10N-04 fonts and formats | S12 |
| L10N-02 Kannada | S14 |

**Reinterpreted for the current stack:** the i18n framework is **i18next + ICU in the RN app** and the same catalogues rendered on the server for the lite web page, push and SMS (no PWA); "Indic fonts without breaking the 3 s load budget" becomes **system Noto/Kohinoor fonts in the app (no bundling)** and system font stacks on the lite page; WhatsApp per-language templates are rows in MSG's `message_template_variants`. **Host mode stays English** in P1.

FND-09 (S2) must already set up i18next with English and the extraction/CI tooling below; this epic adds languages, not the framework.

## 2. Key decisions

| Decision | Chosen | Rejected alternative | Why |
| --- | --- | --- | --- |
| App i18n library | **i18next + react-i18next + i18next-icu** | FormatJS `react-intl` | i18next has lazy namespaces, a parser for key extraction and works the same in Node for the server-rendered pages; ICU plugin keeps plural/select syntax translators know |
| Catalogue location | New **`packages/i18n`** (`locales/{en,hi,kn}/{common,guest,errors,notify}.json` + typed keys) shared by mobile and API | Catalogues inside `apps/mobile` | API renders the lite page, push and SMS text in the guest's language from the same strings |
| Catalogue delivery | **Bundled** in the app (~25 KB per language) | OTA / remote catalogues | Works offline at venues; no extra request on cold start |
| UI string translation | Professional translator + native reviewer, JSON in repo, CI fails on missing keys; pseudo-locale (`en-XA`, +40% length) for layout tests | Crowd / machine-translated UI strings | Older guests; trust; legal text (consent notice) must be reviewed |
| Machine translation of host text | **Google Cloud Translation v3** behind `TranslationProvider` + `FakeTranslationProvider` | AI4Bharat IndicTrans2 self-hosted; Bhashini; an LLM API | IndicTrans2 needs a GPU box to run; Bhashini availability/SLA unproven; an LLM gives better tone but more cost/latency to tune — revisit after pilot feedback (same interface) |
| Proper nouns | **Glossary placeholders**: replace glossary terms with tokens before MT, substitute target terms after | Google glossary resources | Per-wedding terms (couple names, venue names) change often; placeholders are simple and provider-neutral |
| What guests see before host review | **Machine translation shown with "Auto-translated · Show original"**; announcements show translations in the composer before send | Show only approved translations | Hosts won't review every note in the week of the wedding; a labelled MT beats English for a Hindi-only grandparent (PO decision) |
| Language preference level | **Guest-level override** (`guests.preferred_language`) over party-level (`parties.preferred_language`, core) over wedding default (`weddings.settings.default_language`) | Party-level only | Grandparents and grandchildren in one party differ; WhatsApp goes to individual phones |
| Dates and numbers | **`date-fns` + `date-fns-tz` with `hi` / `kn` locales** in `packages/domain`; Latin digits; Indian digit grouping helper | `Intl.DateTimeFormat` on Hermes | Hermes `Intl` depends on the OS ICU version (Android 9 differs); date-fns gives identical output on device and server |
| Fonts in the app | **System fonts** (Android: Noto Sans Devanagari / Kannada; iOS: Kohinoor Devanagari, Kannada Sangam MN / Noto Sans Kannada) with per-script line-height tokens | Bundle subset Noto fonts | Zero bundle cost; system fonts render conjuncts correctly; brand Latin font falls back per glyph |
| Fonts on lite web | System font stack, `lang` attribute set, no webfonts | Self-hosted subset woff2 with `unicode-range` | Budget Android browsers already ship Noto; keeps page < 50 KB |
| Host-mode language | English only in P1 | Translate host UI | Hosts and planners use English; halves translation work |

## 3. Data model

DDL: [`sql/20-l10n.sql`](./sql/20-l10n.sql). **Schema check passed** (`scripts/check-schema.sh arch_l10n 000-core.sql 20-l10n.sql` → `OK: 19 tables`; also with `07-msg.sql` → `OK: 28 tables`).

| Table / change | Purpose | Notes |
| --- | --- | --- |
| `guests.preferred_language` (ALTER core) | Per-guest override, nullable | `CHECK IN ('en','hi','kn')` |
| `parties.preferred_language` (core, unchanged) | Party default, set by host at import or by guest | Values validated by Zod (`SUPPORTED_LANGUAGES`); see §14 |
| `weddings.settings.default_language`, `.languages` (core jsonb, owned by SET-06) | Wedding default and enabled languages | No DDL |
| `content_translations` | One row per (entity, field, language): `text`, `status` (`machine`, `approved`, `edited`, `stale`, `failed`), `source_hash`, reviewer | Polymorphic (`entity_type`, `entity_id`) so source modules stay the only writers of their tables; deleted with the wedding; entity deletes clean up via the `content.deleted` event |
| `translation_glossary_terms` | Global seed (Haldi, Mehendi, Sangeet, Pheras…) + per-wedding terms (couple names, venues) | Unique per wedding/language/term (case-insensitive) |
| `translation_usage` | Characters sent to MT per wedding per month | Cost cap (default 200k chars/wedding) |
| `message_template_variants` (07-msg) | WhatsApp/SMS per language with approval status | L10N seeds `hi`/`kn` rows |

**Stale detection:** when a source field changes, its `sha256` no longer matches `source_hash` → rows flip to `stale` and are re-translated; host-`edited` rows become `stale` but are **not** overwritten until the host accepts the new MT.

## 4. API

| Method | Path | Caller | Purpose | Notable errors |
| --- | --- | --- | --- | --- |
| PUT | `/v1/guest/preferences/language` | guest | `{ language, scope: 'me' \| 'party' }` (party scope only for the primary guest) | `L10N_LANGUAGE_UNSUPPORTED` |
| GET | `/v1/weddings/:wid/translations?language=&status=&cursor=` | owner, co_host, planner_member | Review queue (source vs translation) | — |
| PUT | `/v1/weddings/:wid/translations/:id` | owner, co_host, planner_member | `{ action: 'approve' }` or `{ text }` (→ `edited`) | `L10N_TRANSLATION_STALE` (409, source changed) |
| POST | `/v1/weddings/:wid/translations/preview` | `msg.compose` | Synchronous MT for the composer: `{ text, sourceLanguage, languages[] }` → `{ hi: "...", kn: "..." }` (glossary applied, rate-limited) | `L10N_MT_UNAVAILABLE` (503), `L10N_MT_QUOTA` |
| POST | `/v1/weddings/:wid/translations/retranslate` | owner, co_host, planner_member | Re-run MT for `stale`/`failed` items | — |
| GET / POST / DELETE | `/v1/weddings/:wid/glossary` | owner, co_host, planner_member | Manage per-wedding terms | `L10N_GLOSSARY_DUPLICATE` |
| PATCH | `/v1/weddings/:wid/guests/:gid` (GST) and `/parties/:pid` | host roles | Host sets a guest's or party's language (GST owns the endpoints; field added) | — |

Guest-facing read endpoints (schedule, inbox) owned by SET/MSG return host text already resolved to the guest's language as `{ text, autoTranslated, original? }`; there is no separate translation endpoint for guests. Desk staff: no access (announcement translations are announcement content).

**Internal module API** (`modules/l10n/index.ts`):

```ts
l10n.effectiveLanguage(guest: { preferredLanguage?, party: { preferredLanguage } }, wedding): Lang
l10n.resolve(weddingId, entityType, entityId, field, lang, sourceText): { text, autoTranslated, original? }
l10n.resolveMany(...)                         // batch for schedule / inbox lists, one query
l10n.t(lang, key, values)                     // server-side ICU rendering from packages/i18n (lite web, push, SMS)
```

Source modules (SET for events/venues/contacts, MSG for message bodies) emit `content.changed { weddingId, entityType, entityId, fields: { name: text } }`; L10N listens.

### Examples

`POST /v1/weddings/:wid/translations/preview`

```json
{ "text": "Buses leave the hotel lobby for the Baraat at 4:15 pm sharp.", "sourceLanguage": "en", "languages": ["hi"] }
```
→ `200 { "hi": { "text": "बारात के लिए बसें होटल लॉबी से ठीक शाम 4:15 बजे निकलेंगी।", "glossaryApplied": ["Baraat"] } }`

`GET /v1/guest/schedule` (GH-02, served by SET) with a Hindi guest:

```json
{ "events": [ { "id": "…", "name": { "text": "संगीत", "autoTranslated": false },
  "notes": { "text": "पार्किंग गेट 2 पर है।", "autoTranslated": true, "original": "Parking is at gate 2." },
  "startsAtLabel": "शुक्र, 16 अप्रैल · शाम 7:00" } ] }
```

## 5. Jobs, events and realtime

| Queue / job | Trigger | Behaviour |
| --- | --- | --- |
| `default` · `l10n.translate` | `content.changed` for a wedding whose enabled languages include non-source languages | Batch fields (≤ 100 segments per provider call), apply glossary placeholders, upsert `content_translations`, add to `translation_usage`; retries 3× with backoff; `singletonKey = entityId:field:lang` debounces rapid edits (30 s) |
| `default` · `l10n.enable-language` | Host enables a language or first guest picks it | Translate all existing wedding content |
| — | `content.deleted` | Delete translations for that entity |
| MSG integration | `msg.resolve` | Each recipient's `language` = effective language; renderer picks the approved template variant in that language, else falls back to `en` and counts `missingTemplateLanguages` |

Announcement bodies: the composer calls `translations/preview` synchronously; on send, MSG stores the shown translations as `content_translations` rows (`entity_type='message'`, status `approved` if the host saw them, else `machine`). No MT call happens inside the fan-out path, so translation never slows the 2-minute target.

## 6. Mobile app

| Mode | Screen | Notes |
| --- | --- | --- |
| Guest | **Language picker** on first open (before the consent notice) and in Settings | Shows each language in its own script ("हिन्दी", "ಕನ್ನಡ", "English"); applies instantly (`i18n.changeLanguage`), saved to MMKV and server |
| Guest | All Guest-mode screens | Translated strings; host content shows "Auto-translated · Show original" toggle where `autoTranslated` |
| Guest | Consent notice (ACC-04) | Notice text per language from `packages/i18n` (legal-reviewed), `notice_version` includes language |
| Host | **Translations** review (Wedding → Languages) | Tabs per language; filter Needs review / Stale; side-by-side source and translation; Approve / Edit; glossary editor |
| Host | Composer (MSG) | Preview tabs per language with editable translation before send |
| Host | Guest detail | Language field (guest and party) |

- **Server errors:** the API returns codes; the app maps `errors.<CODE>` keys, so error text is localised with no server change.
- **Typography:** theme tokens `lineHeight` multiplied per script (Devanagari 1.5, Kannada 1.6); no fixed-height text containers; tested at 200% font scale on a 5" screen.
- **Device locale:** default to device language if it is `hi`/`kn` and the guest hasn't chosen; otherwise the server's effective language.
- **Push:** rendered on the server in the guest's language (MSG); `push_devices.locale` lets host pushes follow the device for staff.
- TanStack Query keys include the language (`['guest', 'schedule', lang]`) so a switch refetches; cached data for the old language is kept for offline.

## 7. Guest lite web

**Applicable.** `/g/:token` renders in the guest's effective language (`?lang=` override, saved to the party), `<html lang>` set, system font stack (`system-ui, "Noto Sans Devanagari", "Noto Sans Kannada", sans-serif`), same catalogues via `l10n.t`. Page weight budget unchanged (< 50 KB HTML+CSS).

## 8. Security and privacy

- **MT data flow:** only host-written wedding content goes to the MT provider — never guest names, phones, dietary or ID data. Google Cloud Translation does not retain content for training (data-processing terms); region note in the DPDP record of processing. Announcement text may contain names the host typed — acceptable under `core` purpose; listed in the privacy notice (VAL-13).
- **DPDP notice language:** the Act lets a data principal read the notice in English or a Schedule VIII language; Hindi and Kannada notices need counsel review (add to VAL-13).
- **Integrity:** translations are written only by L10N; hosts can edit; audit log `translation.edit`, `translation.approve`.
- **Rate limits:** `translations/preview` 30/min per wedding; monthly character cap per wedding.
- **Injection:** translated text is treated as untrusted — escaped in the lite page; WhatsApp variables sanitised (no newlines > 2, max length) as for source text.

## 9. Scale and performance

- MT is off the hot path (async jobs; preview is a single call per compose). A 2,000-guest wedding has ~30 events/venue notes and ~40 announcements → < 50k characters per language.
- `resolveMany` uses `content_translations_entity_idx`; one query per screen.
- App: three catalogues bundled (~75 KB total, uncompressed JSON); only the active language is parsed at startup (lazy `require` per language) to protect the < 3 s cold start on budget Android.

## 13. Risks and open questions

| Risk / question | Mitigation / owner |
| --- | --- |
| MT quality for wedding register (honorifics, "aap") | Glossary + host review + guide prompts in the review screen; revisit an LLM provider after pilots |
| Kannada/Hindi WhatsApp templates rejected or recategorised | Keep wording identical in meaning to approved `en`; fall back to `en` variant automatically |
| Unicode SMS costs ~2× per message | PO decision: English-only SMS fallback (short text + link) vs localized |
| Text expansion breaks layouts at large font sizes | Pseudo-locale tests; no fixed heights |
| Older Android fonts missing rare conjuncts | Device lab check on Android 9; bundle a Noto subset only if a real defect appears |

**Product owner decisions:** (1) show unreviewed machine translations to guests (recommended, labelled) or only approved; (2) SMS fallback language; (3) budget for professional translation of UI strings and legal notice; (4) host UI stays English in P1; (5) MT provider (Google recommended) and per-wedding character cap.
