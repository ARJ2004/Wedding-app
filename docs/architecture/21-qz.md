# E21 — Couple quiz (QZ)

## 1. Summary

A host builds a multiple-choice quiz about the couple (text or picture options). At the Sangeet the MC runs it live: questions show on the venue projector, up to 500 guests answer on their phones against a server-timed clock, and a leaderboard shows between rounds. The same quiz can also be played on your own, any time before the live round (async mode).

| Story | Covered by |
| --- | --- |
| QZ-01 Quiz builder | Host-mode editor, `quizzes` / `quiz_questions` / `quiz_options` |
| QZ-02 Live quiz mode | Split into **QZ-02a** live engine + guest player and **QZ-02b** projector screen + host console |
| QZ-03 Leaderboard and async mode | Leaderboard on screen and phone; async session per quiz |
| QZ-04 (new, optional) | Guest lite web player for guests without the app. Needs a product owner decision |

Phase: Pilot, **S14 (31 May – 13 Jun 2027)**.

**Changes for the new stack.** The backlog assumed a PWA guest and Redis pub/sub. The guest player is now a screen in the React Native app's Guest mode. Realtime uses the FND hub: SSE plus Postgres `LISTEN/NOTIFY` with the `realtime_events` replay table (`01-fnd.sql`). Answers come in as plain HTTPS POSTs. The projector is a **web page served by the API** (decision below), not part of the app.

## 2. Key decisions

| Decision | Chosen | Rejected alternative | Why |
| --- | --- | --- | --- |
| Projector screen | Server-rendered page at `/screen` (about 15 KB of vanilla JS plus `EventSource`), opened on whatever laptop is plugged into the venue projector. It pairs with the wedding using a 6-digit code that the host types into the app. | RN app on a tablet, mirrored with Chromecast or AirPlay | Venue AV runs from a laptop over HDMI. Casting needs the tablet and the dongle on the same Wi-Fi and often fails at venues, and AirPlay is iOS-only. Any browser works, and there is nothing to install. |
| Who drives the quiz | Host app console **and** the screen page's keyboard. A presentation clicker (PageDown/→) means "next step". | Host app only | The MC usually stands at the laptop with a clicker. If the host's phone is on bad 4G, the quiz must not stall. |
| Transport | **SSE down** (FND hub, channel `quiz:<sessionId>`) **plus POST up** for answers | WebSocket | Each player sends one answer per question, so the uplink is tiny. SSE already exists, replays with `Last-Event-ID`, passes mobile proxies and needs no sticky sessions or upgrade handling in Nginx. A WebSocket would be a second realtime stack for no gain. |
| Question delivery | The SSE event carries only `{questionId, opensAt, closesAt, version}`. Phones `GET` the question during a 3 s "Get ready" lead-in, served from an in-process LRU cache. | Full question text in the SSE payload | `realtime_events.payload` is capped at 4 KB, and Devanagari takes 3 bytes per character. With hi/kn translations a question doesn't fit. One code path also serves reconnects. |
| Timing fairness | Server-authoritative. `opens_at`/`closes_at` are set by the server. `elapsed = received_at − opens_at`. Answers are accepted until `closes_at + 1.5 s` grace. Phones sync their clock only to **display** the countdown (`GET /v1/time`, best of 3 by round-trip time). | Client-reported answer time | A client-reported time is trivially spoofable. The 3 s lead-in absorbs SSE delivery spread. The **speed bonus can be switched off** per quiz, for elders and bad networks. |
| Scoring | Correct = `points × (0.5 + 0.5 × (1 − elapsed/limit))` when the speed bonus is on, else `points`. Ties are broken by lower total elapsed time. Scored in one statement when a question closes. | Scoring each answer as it arrives (live) | Batch scoring keeps the answer insert to one cheap statement under burst, and the correct option never touches the request path before reveal. |
| Closing a question | pg-boss job `quiz.close-question` with `startAfter = closes_at + grace` (singleton key `session:question`), plus host/screen command. The close is idempotent through `state_version`. | `setTimeout` in the API process | It survives an API restart. Fairness doesn't depend on close latency, because late answers are refused by timestamp anyway. |
| Live vs async | Separate sessions and separate leaderboards. The async window closes when a live session starts. A guest who played async can't join live for the same quiz. No answer reveal in async until the async window closes. | One combined leaderboard | Otherwise async players know the answers before the Sangeet. Needs a product owner decision (§13). |
| Translations | L10N `content_translations` (entity types `quiz_question`, `quiz_option`), loaded once per session into the cache | A jsonb column on questions | Reuses the L10N review flow. Needs L10N to extend its `entity_type` CHECK. |
| Live counters on screen | Screen polls `GET …/screen/state` once a second while a question is open (answer count) | `rt_publish` on every answer | 500 answers would mean 500 events × 500 subscribers. Only the screen needs the count. |

## 3. Data model

SQL: [`sql/21-qz.sql`](sql/21-qz.sql). Depends on `000-core.sql` only. **Schema check: `OK` (23 tables in `arch_qz`). It also applies cleanly after every other design file present (01–20).**

| Table | Purpose | Notes |
| --- | --- | --- |
| `quizzes` | One quiz per wedding (several allowed), optionally tied to an event (usually the Sangeet) | `speed_bonus`, `default_time_limit_s`, async window (`async_enabled`, `async_opens_at`, `async_closes_at`) |
| `quiz_questions` | Ordered questions; `kind` `mcq` / `image_mcq`; optional `prompt_media_id` | `UNIQUE(quiz_id, position) DEFERRABLE`, so a reorder is one transaction |
| `quiz_options` | 2–6 options; label and/or picture | Partial unique index makes **exactly one correct** option per question (the service also checks there is at least one before `ready`) |
| `quiz_sessions` | One play: `live` (state machine) or `async` | At most one open live session per quiz, one async session per quiz. `join_code` is unique per wedding while open. `state_version` gives optimistic concurrency for commands and lets clients drop stale events. |
| `quiz_screens` | Projector pairing | Not wedding-scoped until paired (deliberate exception). Code and secret are stored as sha256. TTL is 10 min unpaired and 12 h paired. |
| `quiz_players` | A guest in a session | `UNIQUE(session_id, guest_id)`. Running totals are denormalised for the leaderboard. `removed_at` lets a host remove a player (rude nickname). Leaderboard index `(session_id, total_score DESC, total_elapsed_ms) WHERE removed_at IS NULL`. |
| `quiz_answers` | One row per player per question; PK `(player_id, question_id)` means the **first answer wins** (`ON CONFLICT DO NOTHING`) | Async inserts the row with `shown_at` when the question is served, so a refresh can't reset the timer |

Images use core `media_objects` (kind `other`, so they never show up in gallery queries by `kind='photo'`), uploaded through the standard upload flow.

**EXPLAIN results** (20 weddings × 500 players × 15 questions = 150 k answers): close-time scoring `UPDATE` uses `quiz_options_one_correct` plus `quiz_answers_session_question_idx`. The top-10 leaderboard is an index scan with `LIMIT` on `quiz_players_leaderboard_idx`. "My rank" is a BitmapOr on the same index. The reveal distribution uses `quiz_answers_session_question_idx`.

Host roles = `owner`, `co_host`, `planner_member` (`can(role, 'quiz.manage')`). `desk_staff` has no quiz access. Guests use a guest JWT for the same wedding. If the quiz has an `event_id`, the guest must be invited to that event (otherwise 404).

**Answer**, the hot path. It is one round trip and one statement:

```http
POST /v1/weddings/7f…/quiz-sessions/3a…/answers
Authorization: Bearer <guest JWT>
{ "questionId": "c1…", "optionId": "o3…" }

200 { "accepted": true, "receivedAt": "2027-06-05T15:31:07.412Z", "locked": "o3…" }
409 { "error": { "code": "QZ_TOO_LATE", "message": "Time's up for this question" } }
```

```sql
INSERT INTO quiz_answers (player_id, question_id, session_id, wedding_id, option_id, received_at, elapsed_ms)
SELECT p.id, s.current_question_id, s.id, s.wedding_id, o.id, now(),
       greatest(0, extract(epoch FROM now() - s.current_opens_at) * 1000)::int
FROM quiz_sessions s
JOIN quiz_players p ON p.session_id = s.id AND p.guest_id = $guest AND p.removed_at IS NULL
JOIN quiz_options o ON o.id = $option AND o.question_id = s.current_question_id
WHERE s.id = $session AND s.wedding_id = $wedding AND s.current_question_id = $question
  AND now() BETWEEN s.current_opens_at AND s.current_closes_at + interval '1.5 s'
ON CONFLICT (player_id, question_id) DO NOTHING
RETURNING option_id, received_at;      -- no row: re-read the existing answer, or explain why it was refused
```

**Host command:**

```http
POST /v1/weddings/7f…/quiz-sessions/3a…/commands
{ "command": "next", "expectedVersion": 12 }
200 { "status": "question_open", "version": 13, "questionId": "c2…", "opensAt": "…15:32:00.000Z", "closesAt": "…15:32:20.000Z" }
```

**SSE event** (channel `quiz:<sessionId>`): `event: quiz.question_open`, `data: {"v":13,"questionId":"c2…","index":4,"total":15,"opensAt":…,"closesAt":…}`.

## 5. Jobs, events and realtime

| Item | Detail |
| --- | --- |
| SSE channels | `quiz:<sessionId>` for players, host and screen. Kinds: `quiz.state` (lobby/ended), `quiz.question_open`, `quiz.question_closed`, `quiz.reveal` `{correctOptionId, distribution:[%]}`, `quiz.leaderboard` `{top:[{name,score}]×10}`, `quiz.ended`. Published with `rt_publish()` in the same transaction as the state change. |
| Reconnect | FND hub replays from `Last-Event-ID`. The app also calls `GET …/state` on foreground. Events carry `v`, and clients ignore `v` lower than the one they hold. |
| Personal results | After `quiz.reveal`, each phone calls `GET …/me` after random jitter of 0–2 s, so 500 requests are spread out instead of arriving at once. |
| pg-boss | `quiz.close-question` `{sessionId, questionId}` on queue `default`, `startAfter = closes_at + 1.5 s`, singleton key, retry 3. It runs the close transaction: status → `question_closed`, score answers, update totals, `rt_publish`. A no-op if the version has moved on. |
| | `quiz.screen-cleanup` cron hourly: delete expired `quiz_screens`. |
| | `quiz.async-close` at `async_closes_at`: ends the async session and publishes final async results. |
| Domain events | `quiz.session_started` → push module may send "Quiz is starting!" (host button, FCM to app guests at that event). `quiz.session_ended` → audit. |
| Auto-end | A live session idle for over 3 h is ended by an hourly sweep (in `quiz.screen-cleanup`). |

**Live state machine:** `lobby → question_open → question_closed → revealed → (leaderboard) → question_open … → ended`. `next` from `revealed` or `leaderboard` opens the next question with `opens_at = now() + 3 s`. On the last question, `next` shows the final leaderboard, and `end` ends the session.

## 6. Mobile app

| Mode | Screen | Notes |
| --- | --- | --- |
| Host | `QuizList` → `QuizEditor` → `QuestionEditor` | Picture options use the shared upload queue. Drag to reorder. The draft autosaves to MMKV while offline and syncs when back online. `Preview` plays it locally. |

| Host | `QuizResults` | Final leaderboard. Share as an image. |
| Guest | Home card "Quiz is live: Join" (deep link `mehfil://quiz/<joinCode>`; universal link `https://<domain>/quiz/<code>` from the projector QR) | A QR scanned without a guest session on the device shows "Open your invite link from WhatsApp first". |
| Guest | `QuizLobby` → `QuizQuestion` → `QuizLocked` → `QuizReveal` → `QuizFinal` | Answer buttons use **letter + colour + shape + label** (never colour alone). The timer ring follows the synced clock. Haptic on lock-in. The screen stays awake (keep-awake) while focused. |
| Guest | `QuizAsync` | One question at a time; score at the end. |

- **State:** live quiz state lives in a Zustand store fed by the SSE client, not TanStack Query, because it changes every few seconds. Query keys: `['quiz', weddingId, 'list']`, `['quiz', quizId]`, `['quizSession', sessionId, 'me']`, `['quizSession', sessionId, 'leaderboard']`.
- **Network:** the answer POST is retried with backoff (300 ms, 600 ms, 1.2 s) until `closesAt + 1.5 s`. A repeat is harmless because the first answer wins. With no network, the screen shows "Reconnecting…" and does not imply the answer counted until the API confirms it.
- **Budget Android:** no Lottie or heavy animation. Images are fetched as CloudFront WebP previews sized for the device. The question image is prefetched during the lead-in.
- **Accessibility:** large-text mode wraps options vertically. High-contrast palette. The host sees a hint to turn off the speed bonus when many guests are over 60.

## 7. Guest lite web

- **Projector screen `/screen`**: a server-rendered HTML shell plus vanilla JS. Pairing code, QR to join, question, timer, distribution bars, leaderboard. Keyboard: Space/→/PageDown = next step, `F` = fullscreen. It works on Chrome, Edge and Safari on a laptop and never needs a guest token.
- **QZ-04 (optional): lite player at `/g/:token/quiz`.** Same endpoints, guest cookie session from the lite web, about 8 KB of JS with `EventSource`. Without it, guests who never installed the app can't play at the Sangeet. This is a deviation from the baseline ("quiz lives in the app"); see §14.

## 8. Security and privacy

- The **correct option is never sent** before `quiz.reveal`. The question body is only served for the current question from 3 s before it opens. Async answers are not revealed until the window closes.
- Tenant scoping on every query (`wedding_id` + session). Another wedding's session returns 404.
- Screen secret: 256-bit, sha256 stored, HttpOnly + Secure + `SameSite=Strict` cookie scoped to `/v1/quiz-screens` and the screen endpoints. It is valid only for its session. The host can revoke it from the console, and it expires after 12 h.
- Pairing codes: 6 digits, 10 min TTL, and only unpaired screens match. `POST /quiz-screens` is limited to 10/min per IP. Pairing attempts are limited to 10/min per host user, which with the TTL makes brute force impractical.
- Rate limits: answers 5/s per guest; join 10/min per guest.
- Personal data is minimal: the display name defaults to first name + last initial and can be edited. A basic word list blocks rude nicknames, and the host can remove a player. No phone numbers appear in any quiz payload. Covered by the `core` consent purpose (taking part is optional).
- Retention: deleted with the wedding through PRV. Guest deletion cascades to `quiz_players` and `quiz_answers`.
- Audit log: `quiz.session.start`, `quiz.session.end`, `quiz.player.remove`, `quiz.screen.pair`.

## 9. Scale and performance

| Stress | Number | How it holds |
| --- | --- | --- |
| SSE connections | 500 players + 1–2 screens + hosts. Worst case about 5 overlapping Sangeets across 50 weddings, so about 2,500 | Node holds idle sockets cheaply. Nginx `worker_connections ≥ 8192`, `proxy_buffering off`, `proxy_read_timeout 1h`. Heartbeat comment every 15 s (FND). `nofile` limit 65 k. |
| Fan-out | About 5 events per question × 500 = 2,500 socket writes, 1 NOTIFY, 1 row read per API process | Trivial |
| Answer burst | 500 POSTs in a 20 s window, about 150/s peak in the first 3 s | One `INSERT … SELECT` (~1 ms). JWT verified without a DB hit. Pool of 20. |
| Question fetch burst | 500 GETs inside the 3 s lead-in | In-process LRU (session, question) → no DB |
| Close + scoring | 500 rows | 2 statements, < 50 ms (EXPLAIN confirmed) |
| Leaderboard | top 10 + rank | Index scan with `LIMIT`; rank is a count over ≤ 500 rows |

The load test is part of QZ-02a: a Node script (`undici` + `eventsource`) runs 500 virtual players from a second machine against a staging box the same size as production. **Pass:** 95% of players get `question_open` within 1 s of publish; p95 answer POST < 300 ms; 0 lost or duplicated answers; API event-loop lag < 100 ms; CPU < 60%. Repeat with 2,500 connections across 5 sessions in OPS-01.

## 14. Deviations from the baseline

1. **Projector screen is a web page served by the API** (`/screen`), next to the guest lite web pages. The baseline lists the quiz as app-only. No change to the stack: same Express app, server-rendered HTML.
2. **Optional QZ-04 lite web player** would extend the guest lite web to the quiz (if the product owner approves).
3. **`quiz_screens` is not wedding-scoped until paired** (`wedding_id` is null before pairing), an exception to "every wedding-scoped table has `wedding_id` NOT NULL".
4. Change request to L10N: add `quiz_question`, `quiz_option` to `content_translations.entity_type`.

`00-overview.md` should note under "Guest lite web" that the API also serves the quiz projector page.
