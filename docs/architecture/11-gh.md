# E11 — Guest home (GH)

## 1. Summary

Guest home is what a guest sees after opening their link. It shows:
- their **personal schedule** (only invited events), with venue map buttons and dress code
- **my travel and status** (with a room placeholder)
- **key contacts** with call and WhatsApp buttons
- the **announcements inbox**
- the **party QR** for desk check-in

It works **offline** from a persisted cache, is **accessible** (large text, high contrast, icon + label, tested with guests over 60), and loads from **one aggregate endpoint** `GET /v1/guest/home`. Guests without the app get the same basics on the server-rendered **guest lite web** page at `/g/:token`: schedule, RSVP, travel status and "get the app", in under 50 KB.

| | |
| --- | --- |
| Stories | GH-01 Guest-mode shell · GH-02 schedule + home aggregate · GH-03 my travel and status · GH-04 contacts · GH-05 accessibility · GH-06 inbox · GH-07 QR · **GH-08 (new) guest lite web home** |
| Phase / sprint | MVP: S4 (GH-01, GH-02), S6 (GH-03, GH-07), S7 (GH-08), S8 (GH-04, GH-05, GH-06) |
| Module | API `apps/api/src/modules/guest-home` (aggregator only, **no tables**) · app `apps/mobile/src/features/guest-home` |
| Not in this epic | App shell, session store, deep links, MMKV persister (APP-01/02/04); data and endpoints of each section (SET, RSV, TRV, ARR, MSG, ROM); OTP/consent screens (ACC/PRV) |

**How the stories change on this stack.** The backlog's E11 is a **PWA**: service worker, < 150 KB JS, browser offline cache.
- GH-01 becomes the **Guest navigator and home screens** inside the RN app. The shell and offline persister are APP-01/APP-04, so GH-01 shrinks.
- "Loads in < 3 s on throttled 4G" becomes app cold start < 3 s (APP) plus home rendered from cache at once.
- The no-install promise moves to the **guest lite web** (new GH-08).
- `150 KB JS` becomes a **50 KB page budget** for the lite web.

## 2. Key decisions

| Decision | Chosen | Rejected alternative | Why |
| --- | --- | --- | --- |
| Data loading | One `GET /v1/guest/home` aggregate (ETag/304), plus section endpoints for detail screens | Each section fetched separately (SET's `/guest/wedding`, `/guest/events`, RSV, TRV, ARR, MSG) | One round trip on a venue network; one persisted cache entry gives a complete offline home. |
| Aggregation | GH service calls each owner's `index.ts` export in parallel (`Promise.all`) | Database view across modules; GraphQL | Keeps module ownership (no cross-module SQL). Eight small indexed reads. |
| Offline | TanStack Query persisted to encrypted MMKV (APP-04), `meta.persist: true`, `gcTime` 14 d, "Updated 10:42" banner | Custom SQLite store | Already built by APP. The home is small (< 30 KB JSON for a 6-event wedding). |
| Maps | "Open in Maps" deep link (`geo:`/Google Maps URL) + venue address; no in-app map SDK | `react-native-maps` with pins | Saves ~5 MB APK and RAM on 2 GB phones. Guests navigate in Google Maps anyway. |
| Guest realtime | **None**: refetch on focus, reconnect, pull-to-refresh and push tap | SSE for guests | Battery and data on budget phones; nothing on guest home needs < 1 min freshness. |
| Party QR | Shows ARR's `checkin_code` QR, cached for offline | QR of the link token | The link token is a login credential (ARR §2). |
| Lite web rendering | Server-rendered `eta` templates (FND), no JS, inline CSS from design tokens | SPA / React SSR | Budget, works on any browser, nothing to hydrate. |
| Lite web page size | Hard budget **≤ 50 KB gzip** for HTML + CSS; images lazy and optional; CI check | Best-effort | The PRD's no-install promise on 2G/3G. |

## 3. Data model

**No new tables. No SQL file** for this epic. GH reads through other modules' exports:

| Section | Source (owner export) | Tables (owner) |
| --- | --- | --- |
| Wedding header, branding, feature flags | `weddings.getGuestView(weddingId)` (SET) | `weddings` |
| Schedule | `events.listInvitedEvents(partyId)` (SET) | `events`, `venues`, `party_invited_events` |
| RSVP state per event | `rsvp.partySummary(partyId)` (RSV) | `rsvps` |
| Travel | `travel.partySummary(partyId)` (TRV) | `travel_*` |
| Arrival status + QR | `arrivals.partyStatus(partyId)`, `arrivals.checkinCode(partyId)` (ARR) | `arrival_state`, `parties.checkin_code` |
| Room | `rooms.guestRoom(partyId)` (ROM-03, P1). Until it is registered, it returns `{ status: 'not_available' }` | — |
| Contacts | `weddings.listContacts(weddingId)` (SET) | `wedding_contacts` |
| Announcements | `messaging.inboxSummary(guestId)` (MSG) | `message_recipients` |
| Consent state | Access token claim `cns` (ACC) | — |

Schema check: not applicable (no DDL). The two GH-relevant hot reads were measured in RSV (party RSVPs 0.3 ms) and SET (invited events).

## 4. API

| Method | Path | Caller | Purpose | Notable errors |
| --- | --- | --- | --- | --- |
| GET | `/v1/guest/home` | guest (`requireConsent('core')`) | Aggregate for the home and schedule, for the **active** member and their party. `ETag` + `If-None-Match` → 304 | 403 `ACC_CONSENT_REQUIRED`, 401 |
| GET | `/v1/guest/events/:eventId` | guest | Event detail (full notes, venue parking notes, dress-code image) | 404 `GH_EVENT_NOT_INVITED` |
| GET | `/v1/guest/announcements`, POST `…/:mid/read` | guest | **MSG endpoints** used by GH-06 | — |
| GET | `/v1/guest/checkin-code` | guest | **ARR endpoint** used by GH-07 | — |
| GET/POST | `/v1/guest/arrivals/status` | guest | **ARR endpoints** used by GH-03 buttons | — |
| GET | `/v1/guest/travel` | guest | **TRV endpoint** behind "My travel" | — |
| GET | `/g/:token` | public / lite session | Lite web home (§7) | 404 page for an invalid link |

SET's planned `/guest/wedding` and `/guest/events` are **covered by `/v1/guest/home`**. SET exposes them only as service exports, not routes (§14).

Shaping rules:
- Only the guest's own party; no phone numbers of party members.
- Contact phones are shown (the host entered them for this purpose, SET).
- Times are UTC; the app formats them in `wedding.timezone`.
- The QR payload is fetched separately (`/v1/guest/checkin-code`) so the home ETag isn't churned by it.
- A section whose source fails is returned as `null` with `"partial": ["travel"]` (no 500). The app keeps the cached section.

## 5. Jobs, events and realtime

No jobs, no SSE. Consumed signals:
- A push `data.link = mehfil://g/…` tap invalidates `['guest', wid, 'home']`.
- On foreground and reconnect, TanStack refetches with `If-None-Match` (304 = a few hundred bytes).

## 6. Mobile app

**Navigation** (GuestNavigator skeleton from APP-01): bottom tabs with **icon + label**, at most four.

| Tab | Screens |
| --- | --- |
| **Home** | `GuestHome`: hero "Next: Mehendi, Sat 9:30 am" with Open in Maps; action cards ("RSVP for 1 event", "Add travel details"); `TravelStatusCard` with ARR's three status buttons (GH-03); latest announcement; quick tiles: My QR, Contacts, Camera (CAM, when enabled), Gallery |
| **Schedule** | `ScheduleScreen` (`SectionList` by day, wedding-timezone dates "Sat 12 Feb") → `EventDetail` (venue, address, Open in Maps, parking notes, dress code, notes, RSVP state → RSV `RsvpScreen`) |
| **Inbox** | `AnnouncementsScreen` (MSG data, GH-06): newest first, unread badge on the tab, image previews, links to the target screen |
| **Family** | Members + switch (ACC-03), `MyTravel` (TRV `TravelHome`), Room card ("Room details will appear here closer to the wedding" until ROM-03), `MyQrScreen` (GH-07: full-screen QR, max brightness, cached), `ContactsScreen` (GH-04: `tel:` and `https://wa.me/<digits>`), Settings (APP: language, large text, high contrast, privacy) |

**Deep links** (APP-02 `linking.ts`): `mehfil://g/home`, `mehfil://g/schedule/:eventId`, `mehfil://g/announcements/:mid`, `mehfil://g/travel`, `mehfil://g/qr`.

**Query keys:** `['guest', wid, 'home']` (persisted), `['guest', wid, 'event', eventId]`, `['guest', wid, 'checkin-code']` (persisted, `staleTime: Infinity` until link rotation), MSG's `['guest', 'announcements']`.

**Offline:**
- First paint comes from the persisted cache (no spinner when data exists).
- The `Banner` "Offline — showing details from 10:42" uses NetInfo (APP-04).
- QR and schedule work fully offline.
- Status buttons and RSVP queue in the outbox.
- Cache encrypted (APP); persisted for 14 days after the wedding, then cleared.

**Performance on budget Android:**
- `FlashList` for inbox and schedule; images use CloudFront WebP at 360/720 widths.
- Camera, scanner and gallery modules are loaded with inline `require` only when opened.
- The home renders ≤ 40 views above the fold.
- Targets: home interactive < 1 s from a warm cache, < 2.5 s cold over 3G with a 304.

**Accessibility (GH-05):**
- FND-10 large-text multiplier (1.3) on top of the OS scale (capped at 2.0); layouts tested at the maximum.
- High-contrast palette; every icon has a visible label.
- Touch targets ≥ 48 dp.
- Dates are written out ("Saturday, 12 February, 9:30 am"), not "12/02".
- TalkBack/VoiceOver labels and headings on all GH screens; no gesture-only actions; reduced motion respected.
- Language from the party preference (L10N later).

## 7. Guest lite web

**Applicable (GH-08)**: the no-install path for the basics.

| Route | Owner | Content |
| --- | --- | --- |
| `GET /g/:token` | GH (landing part from ACC) | No session → ACC landing (who are you + OTP). Session but no consent → redirect to PRV `/g/:token/consent`. Otherwise the **home page** sections below. |
| `/g/:token/rsvp` | RSV-01b | RSVP form |
| `/g/:token/travel` | TRV | Travel form |
| `POST /g/:token/status` | ARR | "I've landed / Running late / At the hotel" |
| `/g/:token/consent`, `/privacy` | PRV | Consent, privacy settings |
| `/g/:token?m=<id>` | MSG | Highlights an announcement (SMS fallback link) |

**Home page sections, in order** (each one is a partial from the same service exports as `/v1/guest/home`):
1. Header: wedding title, dates, small cover (lazy, ≤ 30 KB WebP, optional).
2. "Hello Sunita" + member switch form (ACC-03).
3. Next event card.
4. **Schedule**: invited events by day, time, venue, "Open in Maps" link, dress code, RSVP chip per member, plus a "Change RSVP" link.
5. **Travel**: summary of what is on file or "Add travel details", ARR's three status buttons, and the party QR as inline SVG for the desk.
6. Latest 3 announcements (MSG) with "See all".
7. Contacts (`tel:` / `wa.me`).
8. **Get the app** block (APP): store badges, "Open in app", Smart App Banner meta.
9. Footer: privacy notice, "Stop WhatsApp updates" (MSG-10), sign out.

**Budget and build:**
- ≤ 50 KB gzip for HTML + CSS (no JS, no web fonts: system font stack; Indic fonts are an L10N-04 concern).
- CSS variables generated from `packages/design-tokens`.
- Base font 18 px; `prefers-contrast: more` and `prefers-color-scheme` honoured; a large-text toggle via `?t=l` cookie.
- CI renders the seeded party home for a 6-event wedding and fails above **50 KB gzip**, or if any `<script>` or third-party URL appears.

**Headers:**
- `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex, nofollow`
- CSP `default-src 'none'; img-src 'self' https://<cloudfront>; style-src 'nonce-…'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'`

**Performance:** p95 TTFB < 300 ms (same parallel service reads).

## 8. Security and privacy

- **Scope:** everything is derived from the guest token or cookie (`wid`, `pid`, `sub`). Nothing is taken from the path except `/g/:token`, which is resolved by ACC.
- **Consent:** the home is gated by consent `core` (ACC `requireConsent`). Before consent, only the landing page renders.
- **Minimisation:** no party member phones, no other parties' data, no host notes. Venue coordinates and contacts are intentionally guest-visible (SET).
- **Offline cache:** encrypted MMKV (APP) and cleared on leave/sign-out. The persisted home includes only the fields above. The QR is not a credential.
- **Lite web:** token-in-URL protections from ACC (no-referrer, log scrubbing), CSRF on every form, no third-party assets.
- **Audit:** reads are not audited (volume). Writes are audited by the owning modules.

## 9. Scale and performance

| Stress | Load | How it holds |
| --- | --- | --- |
| After an announcement to 2,000 guests | ~2,000 home refetches within ~5 min ≈ 7 req/s per wedding | ≈ 8 indexed reads, < 30 ms DB time; most are 304s. 50 weddings at once still < 50 % of one API process. |
| Wedding morning | Guests open the schedule repeatedly | Served from cache; 304 revalidation |
| Lite web | Budget phones on 2G/3G | 50 KB cap ≈ 2–3 s on 2G; no JS to parse |
| Venue Wi-Fi drops | — | Full offline home, QR and schedule |
