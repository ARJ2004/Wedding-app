# E27 — P2 candidates (VOX / WSH / WL / PWP)

## 1. Summary

These are lighter-weight designs for the five P2 candidates. They are picked in priority order at Gate 3 (27 Jun 2027) and slot into S18–S20. Each gets one section in §2 with the approach, provider choice, data, rough estimate and main risk. The other sections cover only what they share. Refine each design properly when its story is picked.

| ID | Candidate | Default slot | Backlog | Revised |
| --- | --- | --- | --- | --- |
| VOX-01 | Voice calls in the guest's language, keypress RSVP | S18 | 8 | **10** |
| VOX-02 | WhatsApp voice-note announcements | S19 | 3 | **5** |
| WSH-01 | Video wishes and guest book | S20 option | 5 | **8** |
| WL-01 | White-label (custom domain + full branding) | S19 | 5 | **6** |
| PWP-01 | Post-wedding pack | S20 option | 8 | **13** (split a/b/c) |
| | **Total** | | **29** | **42** |

**Changes for the new stack.** There is no PWA, so "branding" means runtime theming in the one React Native app plus the guest lite web. Video uses ffmpeg in the pg-boss worker on the EC2 box rather than ECS tasks. Voice and TTS go behind interfaces, like `MessagingProvider`.

**Shared building blocks.** Build these once, in whichever candidate comes first:

- **`TtsProvider`**, used by VOX-01 and VOX-02.
- **`video_renders` + the `video` pg-boss queue (ffmpeg)**, used by VOX-02, WSH-01 and PWP-01.
- **`PdfRenderer` (headless Chromium)**, used by WSH-01 and PWP-01.

## 2. Key decisions (one section per candidate)

### VOX-01 — Voice calls in the guest's language

**What:** the host picks a set of guests (filters from the RSV chase: no reply after N days, guests over 60, no WhatsApp delivery) and a script. The system calls each guest during a set window and plays a message in their language. For RSVP chase it asks "Press 1 if you're coming to the Sangeet, 2 if not, 9 to hear again", for up to 3 events. Results land on the RSVP dashboard with `source='voice'`.

| Decision | Chosen | Rejected | Why |
| --- | --- | --- | --- |
| Voice provider | **Exotel** (primary) behind `VoiceProvider`; **Plivo** as the second adapter | Twilio | Exotel is India-native: Indian virtual numbers, operator relationships, IVR flows with DTMF capture through a "passthru"/gather webhook, ₹ billing. Plivo has a clean API (`<GetDigits>`, `<Play>`) and is cheaper than Twilio. Twilio's outbound calling in India is pricey and needs a local-number setup. |
| TTS | **Pre-rendered audio** from Google Cloud Text-to-Speech (hi-IN, kn-IN, en-IN, ta, te, mr…) through `TtsProvider`. The MP3 is stored as `media_objects`, and the provider is told to `Play` its URL. | The provider's built-in `<Speak>` | Built-in TTS voices vary by provider, and Polly has no Kannada. Pre-rendering means the host **listens before sending**, the audio is cached across 300 calls, and providers can be swapped. |
| Script text | Host writes it once. L10N machine-translates it, and the host reviews (existing L10N-03 flow). Names and events are inserted as separate TTS clips joined at play time ("Namaste" + `<name>` + body). | One TTS clip per guest | 300 clips vs 1 + names; review stays practical |
| Fan-out | pg-boss `voice.place-call` per `voice_calls` row, with a concurrency cap (provider calls per second, e.g. 2) and only inside `window_start`–`window_end` in the wedding timezone. Retry once after 2 h on no-answer or busy. | Provider bulk campaign API | Keeps idempotency (`UNIQUE(campaign_id, guest_id, attempt)`), the calling window and results in our hands |
| DTMF → RSVP | Provider webhook → `voice` module → `rsvp.recordFromChannel({guestId, eventId, status, source:'voice'})` (RSV export) | Writing `rsvps` directly | Module boundary; RSV owns `rsvps` |

- **Data:** `voice_campaigns`, `voice_calls` in [`sql/27-p2.sql`](sql/27-p2.sql). Needs RSV to add `'voice'` to `rsvps.source` (change request, §14).
- **API:** `POST /v1/weddings/:w/voice-campaigns` (draft, with audience filter), `POST …/:id/preview-audio`, `POST …/:id/schedule` (`Idempotency-Key`), `GET …/:id` (counts by status, cost), `POST /v1/webhooks/voice/:provider` (signature-verified). Host roles only; desk staff 404.
- **Mobile:** Host mode only: a "Call guests" flow from the RSVP chase screen; preview audio player; results list. Nothing changes for guests.
- **Cost:** about ₹0.6–1.5 per answered minute plus about ₹0.1–0.3 per attempt. 300 guests × 1 min is roughly ₹300–600 per campaign. Paid add-on (BIL-04).
- **Compliance:** automated calls fall under TRAI TCCCPR. Service/transactional calls need the provider's registered number series and DLT entity and content registration. Calls only between 09:00 and 21:00 (enforced by CHECK). The script names the couple and says "from Mehfil". Opt-out by keypress (`8`) suppresses future calls (reuse `messaging_opt_outs` with a `voice` channel; MSG change request).
- **Estimate:** 8 → **10**. The two provider-facing interfaces (TTS + voice), webhook security, calling-window scheduler and RSV integration are each about 2 pts.
- **Main risk:** **regulatory and answer rate.** Unknown numbers get ignored or marked spam by Truecaller, and DLT/voice registration for the number is a long-lead admin task like VAL-10. Mitigation: start provider KYC and DLT registration at Gate 3, not in S18. Send a WhatsApp heads-up ("Mehfil will call you from 080-…") before the campaign. Measure answer rate in one pilot before selling it.

### VOX-02 — WhatsApp voice-note announcements

**What:** the host records a voice note in the app (or generates one with TTS from text) and sends it to selected groups as an announcement.

| Decision | Chosen | Rejected | Why |
| --- | --- | --- | --- |
| Delivery format | **Outside the 24 h service window:** render the audio onto a still image (the couple's cover photo + "Voice message from Ananya & Rohan") as an MP4 with ffmpeg (`video_renders.kind='voice_note_video'`). Send it as a **video-header** announcement template. **Inside the 24 h window** (guest messaged us recently): also send a native WhatsApp audio message (OGG/Opus). | An audio template header | WhatsApp template headers support text, image, video, document and location, **not audio** (verify with the BSP at pick time). Most guests are outside the window, so the video path is the main one. |
| Recording | RN audio recorder → AAC/M4A, max 90 s, uploaded with the standard presigned PUT (`kind='other'`). Waveform preview, re-record. | Recording in the web console | The host app is the console in this stack |
| Other channels | Push + Announcements inbox play the original audio in-app. SMS fallback sends a link to the guest lite web page with an `<audio>` player. | | Elders without WhatsApp still hear it |

- **Data:** `video_renders` (shared). The MSG `messages` row references the rendered `media_id`. MSG must add `'video'` to `message_template_variants.header_kind` and add an audio session-message type (change request).
- **Estimate:** 3 → **5**. Video render job + MSG changes + recorder UI.
- **Main risk:** **template approval and policy.** A video-header template must be approved per language. Meta may restrict generic "media announcement" templates as marketing (higher price, opt-in rules). Validate with the BSP before committing the slot.

### WSH-01 — Video wishes and guest book

**What:** guests record a short video wish (≤ 60 s) or write a text wish. The couple gets a compiled **wish reel** (MP4) and a **guest book** (PDF: text wishes + poster frames with QR codes to each video).

| Decision | Chosen | Rejected | Why |
| --- | --- | --- | --- |
| Data | A wish is a `feed_posts` row (`kind='wish'`), with the video in `feed_post_media` (`media_objects.kind='video'`). Works in feed mode `wishes_only` even if the feed is off. | A separate wishes table | Same moderation, private-wish audience and retention (E22). |
| Client compression | Record at 720p and compress on the phone to H.264/AAC MP4 at about 2.5 Mbit/s (≤ 25 MB for 60 s) before the presigned PUT. iOS HEVC is converted on the phone. | Upload raw | Raw 1080p/4K clips are 100–400 MB, impossible on venue networks |
| Server processing | **ffmpeg in the worker** on the `video` queue (concurrency 1, `nice 19`). Per wish: `ffprobe` validation, `-movflags +faststart` remux (no re-encode when H.264), poster JPEG, duration cap. A re-encode happens only when the codec is unexpected. | **AWS Elemental MediaConvert** | Per-wish work is a sub-second remux, so a managed transcoder adds IAM, job templates, S3 events and status polling for no gain. MediaConvert stays the fallback behind `VideoRenderer` if reels push box CPU > 70%. It is cheap: roughly $0.01–0.02 per output minute. |
| Reel | ffmpeg concat with title cards (guest name), normalised to 720p30 and loudness-normalised. Runs **at night (02:00–05:00 IST)** after the host taps "Make reel". 100 wishes × 30 s ≈ 50 min output ≈ 25–50 CPU-minutes. | Rendering immediately | Keeps the CPU spike away from live events on the single box |
| Guest book PDF | HTML template → PDF with **headless Chromium** (`PdfRenderer`), which shapes Devanagari and Kannada correctly | `pdfkit` | pdfkit doesn't do complex-script shaping, so Hindi conjuncts render broken |

- **Data:** existing E22 tables + `video_renders.kind='wish_reel'`.
- **Mobile:** Guest: `WishRecord` (front camera, 60 s timer, retake, compress progress) inside `WishesCompose`. Host: `WishesBook` gains "Make reel" and "Download book".
- **Estimate:** 5 → **8**. Recording and compression on budget Android, the video queue, reel compositing and the PDF renderer are each real work.
- **Main risk:** **CPU on the single EC2 box and budget-Android recording.** On-device compression on a 2 GB phone can take about 60 s and may crash. Mitigation: 720p cap, background upload, a nightly render window and the MediaConvert fallback. Test on the device lab early.

### WL-01 — White-label

**What:** a planner (or venue) uses their own domain for guest links (`invites.shaadiplanners.in/g/<token>`) and full branding: logo and colours on the guest lite web and in the app's guest mode, no "Powered by Mehfil" on the Planner plan, and a branded email sender.

| Decision | Chosen | Rejected | Why |
| --- | --- | --- | --- |
| TLS for custom domains | **Caddy with on-demand TLS** (Let's Encrypt). Its `ask` hook calls `GET /internal/domains/allowed?domain=` (checks `custom_domains.status='verified'`). Caddy replaces Nginx as the edge proxy. | (a) certbot + generated Nginx server blocks + reload from the worker; (b) CloudFront distribution + ACM cert per domain | (a) needs the worker to have root-level reload rights and a bespoke renew loop. (b) needs a second DNS validation record from every planner and is overkill on one box. Caddy does issue and renew with no code. **CloudFront + ACM is the path when we go multi-box.** |
| Domain verification | Planner adds `CNAME invites.x.in → domains.mehfil.app` and `TXT _mehfil.invites.x.in = <verify_token>`. The `wl.verify-domain` job polls DNS. | HTTP challenge only | Proves ownership before we request a certificate (Let's Encrypt rate limits) |
| Branding source | Reuse **PLN-04 `organization_branding`** (`18-pln.sql`). WL-01 only adds `custom_domains` and a "hide Mehfil badge" entitlement. | A new brand table | No duplication |
| App links | Custom domains serve the **lite web**. Its "Open in app" button goes to `https://<main domain>/g/<token>`, which is a universal/app link. | Adding planner domains to the app | iOS associated domains and Android intent filters are **compiled into the binary**, so a new planner domain would need an app release. |
| Branded app binaries | **Not offered.** The one Mehfil app themes itself at runtime from the wedding's org branding. | A separate store app per planner | Apple guideline 4.2.6 rejects template or white-label apps unless each is submitted from the client's own developer account. Separate binaries also multiply release work. Only a large enterprise deal (their account, their listing, priced accordingly) would justify it. |
| Email sender | Branded display name only (`"Shaadi Planners via Mehfil" <no-reply@mehfil.app>`) | Sending from the planner's domain | Needs SPF/DKIM on the planner's DNS; offer later |
| WhatsApp sender | Stays Mehfil's WABA. The planner name goes in the template footer (PLN-04 `show_in_messages`). | A WABA per planner | Meta business verification per planner takes weeks; not for P2 |

- **Data:** `custom_domains` in [`sql/27-p2.sql`](sql/27-p2.sql). Link generation (MSG/ACC) picks the org's active custom domain when one exists.
- **Estimate:** 5 → **6**. Includes the Nginx → Caddy edge swap and its SSE settings (`flush_interval -1`).
- **Main risk:** **an edge-proxy change on the single production box** shortly before sales start (S19), plus Let's Encrypt rate limits if many domains are added at once. Mitigation: switch the edge to Caddy in S17 (hardening), behind the same `infra/` config review, with a rollback to Nginx.

## 8. Security and privacy

- **Voice (VOX-01):** phone numbers go only to the voice provider (processor agreement); call recordings are off. Keypress results are audit-logged as RSVP changes. Opt-out is honoured.
- **Videos (WSH-01):** they are personal data with faces. They follow photo retention and need `photos` consent. Private wishes are never public.
- **Custom domains (WL-01):** only verified domains get certificates (`ask` hook). Guest tokens on custom domains are the same tokens; the lite web sets cookies host-only.
- **Shipping addresses (PWP-01b):** deleted 30 days after delivery.

## 9. Scale and performance

The single-box risk is the `video` queue's CPU. It runs at concurrency 1 with `nice`, has a nightly window for reels, and the MediaConvert fallback sits behind `VideoRenderer`. Voice calls are rate-limited by the provider, not by us. Custom domains add TLS handshakes, which is trivial at our scale.

## 10. Testing plan

Each provider gets a fake (`FakeVoiceProvider` that simulates DTMF webhooks, `FakeTtsProvider` that returns a silent MP3, `FakeVideoRenderer`). e2e tests cover the calling window, idempotent fan-out, and DTMF → RSVP with `source='voice'`. Golden-file ffmpeg tests use a 3-clip fixture. PDF snapshot tests use Hindi and Kannada text (shaping check). Domain verification is tested against a stub DNS resolver. Device lab: 60 s wish recording on Android 9 / 2 GB.

## 14. Deviations from the baseline

1. **New pg-boss queue `video`**, in addition to `messaging`, `media` and `default`, with ffmpeg installed on the worker host.
2. **WL-01 replaces Nginx with Caddy** as the edge proxy (on-demand TLS for custom domains). The overview's Deploy row would change to "Caddy → PM2".
3. **Headless Chromium on the worker host** for `PdfRenderer` (WSH-01, PWP-01b).
4. **Change requests to other epics:**
   - RSV: add `'voice'` to `rsvps.source`.
   - MSG: add `'video'` to `message_template_variants.header_kind`, an audio session-message type, and a `voice` opt-out channel.
